# WeiboAP 同步落到助手目录，并显示助手名

## 问题

把 skill 同步给 WeiboAP 之后，WeiboAP 里读不到它。

工具当前把 WeiboAP 的「全局」写入点认作 `claude-code-plugins-custom/skills/custom`。经查证，这是 WeiboAP 从服务端下载 skill 的**缓存目录**，由同级的一份清单登记内容（当前 28 条），WeiboAP 按清单点名装配到各助手目录，从不遍历该目录。我们放进去的两条软链不在清单里，建链后清单又被 WeiboAP 重写过一次，仍然没有收录它们。也就是说这个入口写得进去、永远不生效，界面上却显示为已同步的 ✓。

真正被加载的是每个助手自己的目录 `Data/agents/<助手 ID>/.internal-plugins/skills`。工具已经把每个助手当作一个独立的域展示，但这些域在界面上叫 `WeiboAP · agent_1776847465710_d5z6cowep` 这样的 ID，用户无法把它和 WeiboAP 里看到的「办公助手」「数据分析」对应起来，页标题和表格里还各重复一遍这串 ID。

用户目前的绕过方式：没有绕过，只能发现同步没生效之后放弃。

## 期望结果

- 在「全局」给 WeiboAP 同步一个 skill 后，**WeiboAP 里能真的用上它**：链接落到每个助手的目录，重启 WeiboAP 后该 skill 出现在助手可用列表里。
- 一个 skill 在部分助手有、部分没有时，界面**如实显示为部分**（如 `2/4`），点补齐能铺满；不再出现"显示已同步但实际无效"。
- 在 WeiboAP 里新建助手后，全局已同步过的 skill **自动出现在新助手那里**，不需要用户想起来手动补。
- 助手在界面上**显示为 WeiboAP 里的名字**（办公助手、数据分析、微博小程序H5开发助手），不再是一串 ID。
- WeiboAP 官方下发的那批 skill 仍能作为来源，**同步到 Claude Code、Codex 等其他工具**。
- 已经建在缓存目录里的两条无效软链被清除。

## 影响对象

WeiboAP 用户（目前是作者本人）。其他 harness 的同步行为不受影响。

## 约束

- 助手名来自 WeiboAP 自己的数据库，工具只读、且随时可能因对方改动而失效；取不到名字时必须安静降级回 ID，不能报错或影响同步。
- 工具不得写入 WeiboAP 的数据库、清单或任何它自己管理的元数据，只建软链。
- 助手目录是 WeiboAP 装配的目标，工具写进去的链接是否会被它后续覆盖或清理，尚未实测。
- 缓存目录必须变成只读来源：能作为同步来源，不能再作为写入目标。

## 范围外

- 往 WeiboAP 的清单里注册 skill，让它走官方安装流程。
- WeiboAP 的「项目」类型（当前账号下没有项目，无法验证它是否也生成同类目录）。
- 本体位置列在同域时重复显示长名字的问题，单独处理。

## 待决问题

- 往助手目录放软链，WeiboAP 下次装配时会不会清掉？（作者实测：同步一个 skill 到某助手，重启 WeiboAP 看是否仍在、是否可用）—— 默认假设：不会被清理，依据是某助手目录中现存 12 个清单之外的 skill 未被清除。若实测被清，本需求整体重新评估。
- WeiboAP 的「项目」是否也生成 `Data/agents/` 下的同类目录？（作者在 WeiboAP 里新建一个项目后即可确认）—— 默认假设：与助手同构，按同样方式处理。
- 助手里有一个疑似废弃的（AB实验测试），扇出时是否也要包含？—— 默认假设：包含，工具不臆测哪个助手该被排除；若干扰明显，再用现有的自动同步排除机制处理。
